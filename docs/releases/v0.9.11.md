# hirdir 0.9.11

The long reports are worked out by the second process, on a processor of its own, and
again by day once the inventory has been quiet for half a minute after a change: the
first person to open the first page no longer waits for them on the processor that
answers everybody.

## New

- **The second process works out the long reports** (P-275). The coverage report, the
  renewal worklist, the summary of the renewal alert and the capacity balance, each for
  the view its page opens with, are worked out ahead by `hirdir-worker`, when it
  starts and each night at five minutes past midnight, and kept in the database, a row
  to each, where the server finds them. Until now the server worked them out itself,
  when it started and each night, and kept them in its memory.
- **By day they are worked out again once nothing has changed for half a minute**
  (P-276). A change leaves the reports of the night stale, and until now the next
  person to open the first page waited while the server worked them out again, about
  four seconds on the fixture of 50,000 items as it was timed for 0.8.0. Now the
  second process does it, 30 seconds after the last change of a run of them, and
  whoever comes after that has them at once. Somebody who looks sooner is answered by the server as before. While
  an import is applied nothing is worked out, each batch being a change; it is done
  half a minute after the import ends.
- **A setting, `reports_ahead_after_seconds`**, under Admin, Settings: 30 unless set, a
  whole number from 0 to 3,600. 0 turns the work by day off and leaves the start and
  the night.
- **Kept reports on Settings say where each is kept**: in the database, worked out
  ahead, or in the server's memory. What the database holds is listed before anybody
  has asked for it, and Check kept reports checks it with the rest.

## Changed

- **The server works out nothing ahead**, at its start or by the clock. A restart of
  the server answers its first request sooner, and what the database holds is still
  good after it.
- **`GET /kept-answers`** lists what the database holds as well as what the server has
  given, and each entry has `ahead`, true where the database holds it.
- **`POST /kept-answers/check`** checks what the database holds too, and writes again a
  row that differed from the answer worked out anew.
- **`hirdir admin reset`** clears what is kept with the inventory it was worked out of.
- **The first page follows the warning period** (P-277). It counts the cover that runs
  out within the days of `renewal_warning_days`, and says how many they are, where it
  said 90 days whatever the setting was. With the setting at its default nothing
  differs. It is so given the view that is kept, as the page of the report is.
- **A check that a change overtakes stops** (P-277). A change stored while Check kept
  reports works leaves every kept answer stale, and from then on the check compares,
  names and counts nothing more, where it named the answer worked out across the
  change as a defect. It says that it was overtaken, `overtaken` in the answer of the
  API, with how many it compared, and is asked again when the inventory is quiet.
- **A request made with a service token holds up no save** (P-277). When a token was
  last used is stored at once, where it was stored with the request and so held the
  one writer's place for as long as the request took: a report or an export asked for
  with a token made every save wait, and refused it after five seconds. This was so
  in every release that has tokens.
- **The hint under the days** of the coverage report and of the end-of-life report
  says the setting in force, where it said 90 and 730 whatever the settings were.
- **What a kept report is good for is the change stored last** (P-277), where it was
  the change with the greatest ID. An ID is made from the clock of the process that
  makes it, so a clock set back, or the two processes changing something in one
  millisecond, could leave a report as it was after a change, until the next one.

## Additional Notes

- Upgrading from 0.9.10 runs one migration, `0015`, which adds the table
  `kept_answers` and changes nothing that is held; it writes no audit event. The
  second process fills the table a few seconds after it starts. See "From 0.9.10 to
  0.9.11" in [Install and operate](../install.md#from-0910-to-0911).
- Going back to 0.9.10 is by the backup the upgrade made, since the schema changed.
  What the table held is nothing to keep.
- **No answer of a report differs**, whoever worked it out, and no request waits for
  the second process. A request that only reads writes nothing: the table is written
  by the second process, and by the check where a row differed.
- **With the second process down nothing is worked out ahead.** The first person to
  ask for a report after a change, or on a new day, waits while the server works it
  out, as everybody's first request after a change did before 0.9.11. About says
  whether the second process runs.
- **Somebody who looks within half a minute of a change** is answered by the server,
  which works the report out itself; the second process then works out the same once
  more for its row, since it cannot see into the memory of the server. That is work
  done twice, on the second processor.
- **The reports are kept with the inventory they were worked out of.** The table is in
  every backup, four rows at the most, and a row is given only for the very state of
  the inventory it is of: after a restore of an earlier backup nothing of a later day
  is given. `hirdir admin reset` clears it.
- **The API gains**, with nothing taken away: `ahead` in each entry of
  `GET /kept-answers`, `overtaken` in the answer of `POST /kept-answers/check`, whose
  `checked` is then fewer than are listed, and the setting
  `reports_ahead_after_seconds`.
- Two independent reviews read the server's side, the first at its first commit and
  the second of the fixes to the first, and proved each finding with a test or a
  measurement. The first found no way for working ahead, or for
  the server's reading of a row, to give a wrong answer; and it found that a check which
  had a row to write again held every other writer for as long as it went on working,
  a save being refused after five seconds; that the same check wrote over a good row
  where a change had overtaken it; that the newest change was told by its ID, which a
  clock set back or two processes in one millisecond put out of order; that one report
  which could not be worked out kept the other three out of the table; and that the
  first page asked for 90 days whatever the setting. The second found that a check
  could write a row again and then fail to store the event that named it, and, older
  than this release, the hold of a service token's request. All are mended and held
  by tests (P-277).
- Known and left: at each look, and at each request for a kept report, the audit trail
  is read back from its end to the newest change, past every sign-in, preview and
  download since: 32 ms past 200,000 of them, measured, which is nothing until an
  inventory is left unchanged through very many sign-ins. It is a note for
  the timing of 1.0.0. And the order in which changes are stored is SQLite's own
  numbering of the rows of the audit trail: PostgreSQL has none, and the trail is to
  have a sequence of its own when PostgreSQL comes.
- **A fault of the Settings page, older than this release, is left.** A setting with a
  long description has a tall row, and its form opens with the row's Change button
  scrolled out of view above it: `busy_response_ms`, `busy_cpu_percent` and
  `reference_file_types` are such, measured at 733, 444 and 526 pixels of row on a
  window of 1280 by 800. The form itself is in view and works. The scenario that holds
  the form beneath its row tries the first setting and the last, so it met the fault
  only when the new setting, with a long description, was the last; that description
  is now two lines. What the page should do with a tall row is the owner's to say.
- Every component is at its latest production release. Nothing is held back.
- Scenarios S01 to S35 and S39 to S53 pass. The long reports worked out ahead have no
  scenario of the requirements: they are held by the tests of the server, by the
  browser scenarios and by the package test.
