# hirdir 0.9.1

What the owner asked for when 0.9.0 was published: one command that loads the examples
into an empty inventory, for a reset to take again, and a restore that keeps set aside
only what undoing it takes.

## New

- **`hirdir admin load-examples`.** On the server, with the service stopped, one command
  loads the fictional inventory of the examples, every file in the load order, into an
  inventory that holds nothing yet, and says how many records each file made.
  `hirdir admin reset` then takes them again, with whatever was added beside them, and
  nothing of the site's own: the command refuses an inventory that holds any record,
  and refuses while an import waits to be applied. Each file is an import like any
  other, listed with the imports and audited as `system`. A file that the site's set-up
  rejects a row of, a choice that was removed, say, stops the load there and names the
  row. Accounts and settings are not touched. There is no page or route for it, as
  there is none for a reset.
- **The examples inside the application.** The package carries a copy of the examples
  in `/opt/hirdir/venv/`, which the command loads, so that a host whose dpkg leaves out
  `/usr/share/doc`, as a minimal or container image does, has them too. The copy in
  `/usr/share/doc/hirdir/examples/` stays, to read and to import by hand.

## Changed

- **A restore tidies what it sets aside.** `/var/lib/hirdir/files.before-restore/`
  holds what undoing the last restore takes: the files that `hirdir.db.before-restore`
  names and the restored database does not. Each restore lets go of what an earlier one
  set aside there, and says how many files; with 0.9.0 they stayed until somebody
  removed them. To keep what a restore set aside beyond the next one, copy
  `hirdir.db.before-restore` and `files.before-restore/` elsewhere first.

## Additional Notes

- Every component is at its latest production release. Nothing is held back. httpx2,
  which the command line calls the API with, is at 2.16.2, and httpcore2 with it.
- Upgrading from 0.9.0 changes nothing that is held: there is no migration, and the
  schema stays at revision `0011`. See "From 0.9.0 to 0.9.1" in
  [Install and operate](../install.md#from-090-to-091).
- Going back to 0.9.0 needs no backup, since no schema changed: it is the one
  `apt install --allow-downgrades` command, and what was entered since is kept.
- The package test carries one `SKIP`: with no migration there is none to make fail, so
  that check is skipped and says so. The pass upgrades and goes back all the same.
- P-165 and P-166 are this release's, each in its row of [Decisions](../decisions.md),
  built as the owner answered. P-166 adds no scenario, as a release of corrections adds
  none: S12 is worked by the command too.
- Scenarios S01 to S35 and S39 to S53 pass.
