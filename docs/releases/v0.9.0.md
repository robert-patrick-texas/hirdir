# hirdir 0.9.0

Reference files. Photographs, maps, sketches and floor plans are kept with the place they
show, the documents of a vendor with the models they are for, and a carrier's papers with
its circuit, each a file that `hirdir` keeps and serves itself, for a closed network with
no way out, or a link to one kept elsewhere. A guide is uploaded once for every model it
covers, a room lists the plans of the floor and the building it is in, and the files are
in the backup and come back with a restore, on the same host or a clean one.

## New

- **References.** A region, a site, a location, a catalog entry, a circuit and an item
  take references: each a file that `hirdir` keeps, or a link to one kept elsewhere,
  with a title and a kind from a list that can be edited (photograph, map, sketch, floor
  plan, administration guide, data sheet, letter of authorization and others). A
  reference may be on any number of records: an administration guide is uploaded once
  and put on every model it covers, and a new edition replaces it on all of them at once.
- **What a record lists.** A place lists its own references and then those of the places
  above it, nearest first, each under the place it is on, so the floor plan of a floor is
  one step from each of its rooms and racks. An item lists its own, those of its model,
  and those of where it is; a catalog entry and a circuit their own. Nothing is copied
  down: taking a plan off a floor takes it from every room beneath.
- **Files that run nothing.** A file is of a kind an Admin allows, the setting
  `reference_file_types`: pictures, PDF, the files of Office and Visio, DWG and DXF
  drawings, plain text and ZIP to start with. A web page, an SVG drawing, a script or a
  program is never taken, and neither is a file whose first bytes are not what its name
  says. A JPEG, PNG, GIF or WebP picture is shown in the page from an address the page
  makes of what it fetched itself, and every other file is downloaded: the content comes
  as an attachment with `nosniff` and a policy that lets nothing of it run.
- **Up to 100 MB a file**, `max_reference_megabytes` in the configuration file; an import
  stays at 20 MB, and every other request with it. `hirdir-setup --renew` gives nginx the
  larger of the two limits, so a site changes a limit in one place.
- **Erased at once.** Taking a reference off the last record it is on, or erasing it from
  all of them, erases its content then and there; the audit event keeps its title, kind,
  file name, size, checksum and the records it was on. The backups on the host keep their
  copy until they rotate out, so that every backup restores whole.
- **In the backup.** The content of each file is kept once, by its checksum, beside the
  database in `/var/lib/hirdir/files`. Each backup puts what it names into
  `backups/files/`, held once among all the backups, linked where it can be; a restore
  takes it from the `files/` beside the backup, checks every file by its checksum before
  it changes anything, and puts back the database and its files together. To restore on
  another host, the backup is copied with the `files/` beside it.
- **In the API, the command line and the web UI**: `/reference-files` and
  `GET .../{hid}/references` under each of the six kinds of record; `hirdir references`
  to add files and links, list, download, change, replace, put on, take off and remove;
  and on the page of each record a section, Files and links, where files are chosen or
  dropped, sent with a bar of how far each has got, a picture opened in a viewer, and a
  reference edited, replaced, put on other records, taken off or erased. Admin › Files
  lists every reference.
- **Roles and audit.** Any role reads and downloads; the Inventory role adds, changes,
  takes off and erases; an Admin chooses the kinds of file. Every upload, link, change,
  new edition, attachment, removal, erasure and download is an audit event; a download
  changes nothing and leaves the long reports kept.

## Changed

- **nginx takes 100 MB.** The snippet's `client_max_body_size` is `100m`, written by
  `hirdir-setup --renew` from the configuration file, and a snippet that differs from the
  shipped one only in its prefix and its limit is renewed: one whose limit a site raised
  by hand in 0.8.0 is given the larger limit of its configuration.
- **The page's content security policy** allows a picture from a `blob:` address of its
  own, and nothing more.
- **`hirdir admin backup`, `restore`, `check` and `reset`** handle the files: `restore`
  takes `--files DIR` and `--allow-missing-files`, puts the files in place before the
  database and the database last, in one step, and sets aside in
  `/var/lib/hirdir/files.before-restore/` the files the restored database does not
  name, beside `hirdir.db.before-restore`; `check` counts the store and names content
  that is missing or that nothing names; `reset` erases every file after its backup. One
  backup or restore is at work at a time, under a lock in the backup directory, and a
  second waits for it. A restore refuses `hirdir.db.before-restore` itself, and
  [Install and operate](../install.md#backup-and-restore) says how to undo a restore.

## Additional Notes

- Every component is at its latest production release. Nothing is held back.
- **Upgrading from 0.8.0 runs migration `0011`**, which adds the two tables of references
  and the list `reference_kind`, and changes nothing that is held. The upgrade makes
  `/var/lib/hirdir/files`, puts `max_reference_megabytes` into the configuration file,
  and writes the snippet with its new limit. The way back is the backup, as
  [Install and operate](../install.md#from-080-to-090) says.
- P-158 to P-164 are the particulars of this release, built as they stand with the
  owner's answers and what the lanes and the two reviews settled, each in its row of
  [Decisions](../decisions.md).
- **For those who build `hirdir`:** the schema and the store came first; the backup and
  the package were built beside the server, the web UI from the server's commit; the
  server was reviewed by a reader who had not written it, and the backup, the setup tool
  and the corrections by a second, whose findings in a restore stopped partway, a restore
  of its own copy and two backups at once were put right before the release.
- `files.before-restore/` grows with each restore until somebody removes it: it holds
  what a restore took out of use, which may be in no backup.
- Scenarios S01 to S35 and S39 to S53 pass.
- **Timing.** A file of 100 MB is uploaded in 0.6 to 1.0 s and downloaded in 0.4 to 0.8 s
  on the host itself, its checksum checked, and what a record lists is answered in about
  50 ms. What 0.8.0 left to the timing of 1.0.0 is left there, with its numbers in
  "Timing at scale" in [Architecture](../architecture.md#timing-at-scale).
