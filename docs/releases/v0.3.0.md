# hirdir 0.3.0

Files and the command line. The inventory can be loaded from CSV and JSON files and
written back to them, many items can be changed at once, and the `hirdir` command works
with the inventory from any machine that can reach the server. Every change to more than
one record is shown before it is made, and is then made whole or not at all.

## New

- **Import.** A CSV or JSON file of tags, vendors, catalog entries, owners or items is
  previewed first: each row is shown as one that creates a record, one that changes it,
  with the fields that change, one that changes nothing, or one that is rejected, with
  the reason. Nothing is changed by a preview. Applying it makes exactly the changes
  that were shown, in one step. If any record it touches was changed by somebody in the
  meantime, nothing is applied, the rows in the way are named, and a new preview is
  asked for.
- **What a file may say.** A blank cell leaves a value alone, and `!clear` clears it,
  so that it inherits again. A vendor or model that a file names and the catalog does
  not have is created and marked unreviewed, so an import does not wait for the catalog.
  A row finds its item by HID, then by vendor, PID and serial number, then by asset
  tag, then by name. A different lifecycle state in a file moves the item under the
  same rules as anywhere else. Importing the same file twice changes nothing the second
  time.
- **Export.** Any list is written as CSV or JSON with the filter, the sort and the
  columns that are on the screen, the HID always first. A JSON export is a file that
  can be imported as it is. A cell that a spreadsheet would run as a formula is written
  so that it does not.
- **The grid.** Rows are selected one at a time, as a range, or as all that match the
  filter, however many that is. The selected rows are copied to the clipboard or
  exported, with the same rows and columns either way.
- **Bulk edit.** One change to many items: an owner, a disposition, a tag put on or
  taken off, a move to another lifecycle state. It is previewed with before and after
  for each item, and applied on confirmation. When two people edit the same rows, the
  second is told which rows the first has changed, and nothing of the second's is
  applied.
- **The Import page** in the web UI: choose a file, read the preview, apply it, and
  look through earlier imports.
- **The command line.** `hirdir items list`, `show`, `set` and `transition`, `hirdir
  import` and `hirdir export`, and lists of vendors, catalog entries, owners and tags.
  An item is named by its HID, serial number, asset tag or name. A list is a table on a
  terminal and the same file as an export when asked for as `csv` or `json`. A change
  to more than one item is previewed and needs `--apply`. The exit code tells a
  rejected row from a conflict from a refusal.
- **Examples.** `examples/` holds a small fictional inventory as CSV and JSON, written
  by exporting a seeded database, so it cannot drift from what the importer takes. It
  loads into an empty installation, and the package carries it in
  `/usr/share/doc/hirdir/examples/`.
- **Starting over.** `sudo hirdir admin reset`, on the server, clears the inventory, so
  that a site can load the examples or test data of its own, try things out, and begin
  again with its real records. It cannot be done from the web UI or the API, whatever
  role a person holds. It refuses while the service is running, takes a backup first,
  and asks for the word `reset`. Accounts, roles and settings stay; `--everything`
  goes back to a fresh installation. See
  [Install and operate](../install.md#start-over).
- **A request that is sent twice is carried out once.** A `POST` that changes the
  inventory takes an `Idempotency-Key`: sent again with the same key within a day, it
  is answered with the first answer and not repeated.
- **Only the fields asked for.** A list takes `fields=name,catalog.pid` and returns
  those fields of each record, with the HID and the version.
- **A vendor has a review status**, as a catalog entry has, so that a vendor an import
  had to create can be found and looked over.

## Changed

- **Nobody waits for a preview.** A preview of more than a hundred rows is worked on a
  copy of the database and holds no other change up. Applying a large file is one step
  and does hold other changes up while it works, about five seconds for each thousand
  rows. A change that has waited five seconds is answered `503` with `Retry-After`,
  was not made, and can be sent again. Reading is never held up.
- **An import never copies an inherited value down.** An export writes the value in
  force. Imported back, a cell that holds what the record inherits anyway leaves it
  inheriting, for an item and its model and for a model and the global stack discount.
- **The setup tool upgrades `hirdir`.** `hirdir-setup` is in the package, so nothing
  but the one `.deb` is ever downloaded. `sudo hirdir-setup --check` asks GitHub whether
  a newer release is published, and `sudo hirdir-setup --upgrade` fetches it, compares
  it with its checksum and installs it. `--proxy http://proxy.example.com:2025/` sends
  the requests through a proxy. A host with no way out is given the file:
  `sudo hirdir-setup --upgrade PACKAGE.deb`. An upgrade is finished by the tool the new
  package brings, so a later version can add a step without a new tool being fetched.
- **Upgrades by themselves, for a site that wants them.** The package ships
  `hirdir-upgrade.timer`, switched off. Turned on with `sudo systemctl enable --now
  hirdir-upgrade.timer`, it checks GitHub each night at a time of its own between 21:00
  and 03:00, local time, and installs a newer release when there is one. The proxy it
  uses is named under `[upgrades]` in `/etc/hirdir/config.toml`.
- **Upgrading never asks a question.** Plain `apt install` does the same upgrade. The settings
  file, `/etc/hirdir/config.toml`, is brought up to date by the package itself: a
  setting that is new in a version is put into the file commented out at its default,
  also where a site has edited the file, and nothing the site wrote is changed. An
  unattended upgrade therefore always goes through. See
  [Install and operate](../install.md#upgrade).
- **Uploads through nginx.** The packaged nginx snippet lets a file of 20 MB through.
  The snippet is now written by the package at install and at each upgrade, under the
  prefix the host already has, and is no longer a file that the package manager asks
  about. A snippet that was edited by hand beyond its prefix is left alone, and the
  upgrade says so. See [Install and operate](../install.md#upgrade).
- **The command line uses `httpx2`**, which takes the place of `httpx` in the package.
- **A row with only a name finds a draft as well.** It used to find active items only,
  and so made a draft a second time.

## Fixes

- The directory of backups is readable by the service and its group only, whoever takes
  the first backup.

## Additional Notes

- Every component is at its latest production release. Nothing is held back.
- 0.2.1 has no `hirdir-setup --upgrade`. Upgrade from it with
  `sudo apt install ./hirdir_0.3.0_amd64.deb`; from 0.3.0 on, the setup tool can fetch
  the next release itself.
- Upgrading from 0.2.1 takes the schema from revision `0003` to `0004`: three tables
  are created and every vendor there is becomes `reviewed`. Going back takes the steps
  under "Going back to the release before" in
  [Install and operate](../install.md#upgrade).
- Files carry the records that exist so far. Locations, addresses, groups, contracts
  and the rest join them as their releases arrive, and a column of a later release,
  such as `location`, is refused as unknown until then. Choices, settings, lifecycle
  rules and accounts are not carried by files.
- An import does not retire a record, and never forces a lifecycle move.
- A preview is applied once, by anybody who holds the Inventory role, so one person may
  prepare a file and another apply it. The job says who did which.
- Importing is slower than the target for the MVP: about five milliseconds a row on the
  build host, so ten thousand rows take some fifty seconds to preview against a target
  of thirty. A row matched by its name alone is slower still against a large
  inventory, because names have no index yet. Both are for the timing work of 1.0.0.
- While a very large file is being applied nobody can sign in, because signing in
  records itself. It is answered `503` like any other change that waits, and works
  again when the apply is done.
- Behind the packaged nginx a body of more than 20 MB is refused by nginx itself, with
  nginx's own page. A file of more than 100,000 rows is refused by `hirdir`. A site
  that wants larger files raises `max_megabytes` under `[files]` in
  `/etc/hirdir/config.toml` and `client_max_body_size` in nginx to the same figure; see
  [Install and operate](../install.md#uploads).
- A cell whose whole value is `!clear` is always read as "clear this field".
- Copying rows in the grid asks the server for them, as an export does, so that the
  clipboard and the file can never differ. The grid's Name column shows the hostname
  when an item has no name of its own; in a copy or an export the `name` column holds
  the stored name, so show the Hostname column as well to carry both.
- `make package-test` imports and exports the examples through nginx, runs the client
  commands from the package, upgrades from 0.2.1, and makes the new migration fail to
  see that the upgrade stops and can be undone.
- The choices this release made where the documentation was silent were put as
  proposals P-41 to P-59 and have been answered, and are D-65 to D-85 in
  [Decisions](../decisions.md). Two answers changed what had been built: anybody with
  the Inventory role may apply a preview, not only the one who made it, and the settings
  file is kept up to date by the package where it was to stay as shipped. Two remain
  proposals: the routes of accounts refuse `Idempotency-Key` (P-48), and the mode of
  the backup directory (P-58).
- Scenarios S12 to S17 of the [build plan](../build-plan.md) pass, with S01 to S11.
