# hirdir 0.2.0

The inventory arrives: vendors, a catalog of models, and items that inherit from it,
move through the lifecycle and keep their history, in a grid that the server sorts,
filters and pages. Upgrading from 0.1.0 is tested as part of the release and keeps
every account, session and audit event.

## New

- **The catalog.** Vendors, with the other spellings an import will accept, and one
  catalog entry for each vendor and product ID: kind, type, function, the four
  end-of-life dates, estimated value, support weight, annual support cost and stack
  discount.
- **Items.** One record for each tracked thing. An item needs only what identifies it: a
  serial number with its catalog entry, or an asset tag, a name or a hostname. Everything
  else may be left blank. The same vendor, PID and serial number twice is refused, and
  so is the same asset tag. A MAC address is accepted in any common notation and need
  not be unique.
- **Set it once, inherit it everywhere.** An item takes its value, weight, cost and
  dates from its catalog entry unless it sets its own, and every page says where a value
  came from. Changing a date on a model shows on every item of it at once, and no item
  is written to.
- **Lifecycle.** The nine states, with a disposition and an expected-online flag. A move
  from one state to another records who, when, from, to and why. Which moves and which
  combinations are allowed is data that an Admin can change, and an Admin can force
  another move with a reason.
- **History.** Every change to an item is kept and shown on its page: what was, what is,
  who and when.
- **The grid.** Items, the catalog, vendors and owners are lists that sort by any
  column, filter on any column and page on the server. Columns can be resized, moved and
  hidden, and the layout and the last filter are remembered. Drafts, retired records and
  archived items are left out until asked for, and are then greyed.
- **Filters.** One way to say which records are wanted, for the grid and the API alike:
  exact, contains, prefix, wildcard and regular expression, on an item's own fields, its
  catalog entry, its owner, its tags and its values in force, joined with AND and OR. A
  short form can be typed: `lifecycle_state:in:Test,Prod hostname:prefix:site2-`. A
  regular expression is bounded in length, in what it costs to prepare and in how long
  it may run, so a bad one is refused and the server goes on answering.
- **Stale edits are refused.** A change made against a copy that someone else has since
  changed is refused with a message and a way to reload, never applied over the newer
  change, also when the two arrive at the same moment.
- **Tags, choices and settings.** Tags on items and catalog entries. The lists that
  fields choose from can be added to, relabelled, reordered and retired. Settings such
  as the stack discount have a default and can be changed by an Admin.
- **Owners.** An item can be given an owner. An owner's people arrive with contacts in a
  later release.
- **API.** All of the above is under `/api/v1`: `/vendors`, `/catalog-entries`,
  `/owners`, `/items` with its history and transitions, `/tags`, `/choices`, `/settings`
  and `/lifecycle-rules`.

## Changed

- **Upgrading.** The package backs the database up, changes the schema and starts the
  service again. A schema change that fails is undone as a whole, and the message gives
  the commands that put the earlier version back. People stay signed in across an
  upgrade. See [Install and operate](../install.md#upgrade).
- **Errors.** A change is stored before it is answered. An error that nobody foresaw is
  answered in the same form as every other, with a request ID to look for in the log.
- **The Admin area** is shown to every role, because tags, choices and lifecycle rules
  are there for all to read. Users, groups, roles and settings still show to an Admin
  only.

## Fixes

- The way back that a failed upgrade printed could not be followed as printed. It now
  names the version to install and gives every command.
- An upgrade no longer prints a warning from systemd about a changed unit file.

## Additional Notes

- Every component is at its latest production release. Nothing is held back.
- Regular expressions use the `regex` package with a time limit. The linear-time engine
  that the design prefers, RE2, has no release of its Python binding for Python 3.15
  yet, and takes over when it has.
- The server's tests moved from `httpx` to `httpx2`, its continuation under Pydantic,
  which the test client now asks for. The command line still uses `httpx` and is to
  follow in 0.3.0. `httpx2` is not in the package.
- The grid is AG Grid Community, used with its stylesheet themes. That keeps the content
  security policy as strict as it was: nothing is allowed from outside the package, and
  no inline style or script.
- The upgrade from 0.1.0 is now part of `make package-test`, together with an upgrade
  whose schema change fails and a fresh install.
- Going back from 0.2.0 to 0.1.0 takes the steps under "Going back to the release
  before" in [Install and operate](../install.md#upgrade), because 0.1.0 cannot read a
  database that 0.2.0 has changed.
- The backup taken before an upgrade is one of the fourteen that the daily timer keeps,
  so it is removed about two weeks later. Copy it elsewhere to keep it.
- Not yet here, and planned for 0.3.0: import and export, clipboard copy, bulk edit, the
  client commands for items, the `fields` parameter of a list, and `Idempotency-Key`.
- The web UI is one file of about 1.3 MB, so the sign-in page loads the grid as well.
- Proposals P-25 to P-39 in [Decisions](../decisions.md) record the choices made in this
  release where the documentation was silent. Each is the working answer until
  confirmed or corrected.
- Scenarios S06 to S11 of the [build plan](../build-plan.md) pass, with S01 to S05.
