# hirdir 0.9.15

What the owner asked when 0.9.14 was published. An account that holds no role no longer
signs in, and is given a role when it is made or brought back. A new access code is not
the one it replaces, and a Generate button puts a code the server makes in the box, on
the Profile and on the two forms where an Admin gives a code. Every list reached from
the menu bar opens at its top. And the lists of contacts, users and operators leave a
cell blank where there is none.

## New

- **Generate** (P-300). Beside the box of a new access code on the Profile, on New user
  and on Access code of a user's page, Generate fills the box with a code the server
  makes, `GET /auth/new-access-code`: groups of four, as many as the setting
  `access_code_min_length` asks for, and nothing stored until the form is saved. On the
  Profile it fills both new boxes and shows the code in clear; the code in hand is still
  asked for, of an Admin too; once changed to, the new code is shown once more, with
  Copy. A code may still be typed. `hirdir profile access-code --generate` does the same
  from the command line and prints the code once.

## Changed

- **An account that holds no role does not sign in** (P-299). Somebody who gives the
  right code for an account with no role, of its own or through a group, is told so
  plainly, with whom to ask, as the Admin set it under Settings, also where the sign-in
  page does not list it; a wrong code is refused as before, in the same words. The
  refusal is an audit event of its own, `sign_in_no_role`. A session of an account that
  holds no role is refused at its next request: an account that loses its last role,
  by its own grant revoked, its group's revoked, being taken out of a group or the
  group deleted, is signed out at once, and one given its first role has any session
  it held ended, so that no older session comes back. A service account that holds no
  role has its tokens refused. `hirdir sign-in` says the same and keeps no session; in
  0.9.14 it signed such an account in.
- **New user asks for a role for a person**, given or through a group, and says why; a
  service account may be made with none. `hirdir admin create-user` still makes a
  person with no role, and warns that it cannot sign in until it is given one.
- **Bring back asks for the role**, which a person must be given and a service account
  may; `hirdir users bring-back` takes `--role`.
- **A new code on the Profile is not the one in hand** (P-300), and is refused at its
  box. An Admin who sets the code of an account from its page, their own too, may give
  the one it had, and gives no current code, as before.
- **A code the server makes is as long as `access_code_min_length` asks**, wherever it
  makes one: an Admin's empty box, Bring back, `hirdir admin`, and Generate. Until now a
  made code was 14 characters whatever the setting said.
- **The lists of contacts, users and operators leave a cell blank where there is none**
  (P-302): no user and no operator of a contact, no contact and no operator of a user, a
  service account's too, and no user behind an operator, where 0.9.13 put words such as
  no operator. What is there is still a link, and Show still narrows each list to its
  gaps. The page of one person still says in words what it is not.

## Fixes

- **Every list reached from the menu bar opens at its top, with the menu bar in view**
  (P-301). Since 0.9.6 a list put the window back where it was when a row of it was
  opened, on any way of coming back to it: after a row opened from far down, pressing
  the list's entry in the menu bar showed the page scrolled down, with the menu bar out
  of view, by 321 pixels on Contacts, 343 on Operators, 613 on Contracts and 4,470 on
  Capacity. Now the page opens at its top from the menu bar and from a link; only Back
  and Forward put the window back where it was. The rows inside the list are still
  where they were, the opened row marked (P-203). A browser scenario presses every
  entry of the menu bar in turn, after a row of each list is opened from its foot, and
  holds each page at its top.

## Additional Notes

- **Upgrade.** No migration: the schema stays at revision `0017`, and nothing that is
  held is changed. An account with no role, such as one brought back under 0.9.14 and
  not yet given one, cannot sign in after the upgrade until an Admin gives it a role;
  a session it held is ended. Find such accounts on the Users page before upgrading.
  See [From 0.9.14 to 0.9.15](../install.md#from-0914-to-0915).
- **An Admin may reset their own code from their own page** under Admin, Users, with no
  current code, as the owner chose; the Profile asks everybody for the code in hand.
- **Next, 1.0.0**: no new feature. Timing at 50,000 items, the upgrade test from every
  earlier release, accessibility, and the documentation complete. After it: the words
  the pages show gone over for plain writing (P-290), and formats for what is typed or
  pasted (P-293).
