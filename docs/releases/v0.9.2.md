# hirdir 0.9.2

What the owner asked for after 0.9.1 was published: a page opens with the menu bar in
view, the product carries the name a site gives it, and the page says whom to ask, the
team that runs the installation.

## New

- **The name of the product.** An Admin gives `hirdir` the site's own name in Admin ›
  Settings, `product_name`, such as `Example Inventory`. The menu bar shows it at its
  upper left, the browser's tab is titled with it, `Items · Example Inventory`, the
  sign-in page says `Sign in to Example Inventory`, and what the pages say of the
  product names it so. Downloaded files begin with it: an export is
  `Example-Inventory-items-20261116T091500-0500.csv`, and the scoreboard's two files
  `Example-Inventory-scoreboard-sites.csv` and `…-operators.csv`; in a file name letters
  lose their accents and anything a file name had better not hold becomes a hyphen. An
  import still guesses the kind of record of a file so named. The server writes the name
  into the page it serves, so the sign-in page shows it before anybody has signed in,
  and no route is open without signing in that was not before. The commands, the
  package, the service, its paths and backups, the API's own name, and the
  documentation keep the name hirdir. A change shows on the Admin's own page at once,
  and on another person's when the page is next loaded.
- **Whom to ask.** An Admin names the team that runs the installation in the same place:
  `help_organization`, `help_email`, `help_phone` and `help_url`, each blank until set.
  About lists them under Whom to ask for everybody who has signed in: the organization,
  the address to write to, the number to call, whose link dials it without its
  extension, and the address of the team's page, opened in a new tab; or says that
  nobody has been named yet, and tells an Admin where they are set. `GET /about` answers
  them, with the product name.
- **Whom to ask on the sign-in page, where an Admin chooses.** `help_on_sign_in`, off
  unless an Admin turns it on, lists them under the sign-in form too, for someone who
  cannot sign in. The sign-in page is seen by anyone who reaches the site, so while it
  is off the page holds nothing of them.
- **A setting that is yes or no.** `help_on_sign_in` is the first, chosen in Admin ›
  Settings as Yes or No.

## Fixes

- **The menu bar stays in view.** Since 0.1.0, opening a page moved the reader's focus
  to its content, and the browser scrolled that content to the top of the window: on
  every page taller than the window, Groups, Addresses, Vendors, Owners, Contracts and
  most others, the menu bar was pushed out of sight, and had to be scrolled back to
  before moving on. A page opened from the menu bar or from a link now begins at its top
  with the menu bar in view, and focus still moves to its content, without scrolling,
  so that a keyboard or a screen reader starts there. Back and Forward leave the window
  where the browser puts it.

## Additional Notes

- Every component is at its latest production release. Nothing is held back.
  SQLAlchemy is at 2.1.9.
- Upgrading from 0.9.1 changes nothing that is held: there is no migration, and the
  schema stays at revision `0011`. The settings are held in the database only once an
  Admin gives one a value. See "From 0.9.1 to 0.9.2" in
  [Install and operate](../install.md#from-091-to-092).
- Going back to 0.9.1 needs no backup: it is the one `apt install --allow-downgrades`
  command. 0.9.1 does not read the new settings; they stay in the database and are in
  force again after the next upgrade.
- P-167 to P-169 are this release's, each in its row of [Decisions](../decisions.md),
  built as the owner answered: a release of their own, set in Admin › Settings and
  audited, the name in all of the web page and in the names of downloaded files, and
  whom to ask on the sign-in page only where an Admin turns that on. They add no
  scenario, as a release of corrections adds none.
- Two browser scenarios are new: one opens long pages from the menu bar and from a link
  and finds the menu bar in view, and one names the product and whom to ask and puts
  them back. The second changes what every other scenario reads, the title of each page
  among it, and so runs by itself, after the others.
- The package test carries one `SKIP`: with no migration there is none to make fail, so
  that check is skipped and says so. The pass upgrades and goes back all the same.
- Scenarios S01 to S35 and S39 to S53 pass.
